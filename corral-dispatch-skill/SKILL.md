# corral-dispatch：当主控，按任务文件分派、审查、收尾

开 agent、送话、等待、取回复、关掉，一律按 corral 技能做。本技能只管：怎么拆、怎么交代、交给谁用哪一档、怎么审、怎么收尾。

## 先确认三件事

1. **你是主控。** 你如果是被委派的 agent（任务文件里写明了你的身份），不要用本技能：照任务文件做，也不要再开别的 agent。
2. **corral 能用。** 按 corral 技能的自检做，你自己也必须是用 corral 开的。
3. **读项目的 AGENTS.md**（或 CLAUDE.md），找下面这些项目规矩。和本技能冲突时，以项目规矩为准；没写的问用户一次，并参照本技能同目录的 `项目AGENTS模板.md`，建议补进 AGENTS.md：
   - agent 名字前缀；任务文件放哪；按什么拆（里程碑、分支、worktree 放哪）
   - 怎么合并（本地合并还是开 PR）、推不推送
   - 私有数据在哪、哪些不能读、哪些操作花钱

   交给哪家、几档、要不要交叉审查，一般不写在 AGENTS.md 里，按第 3 节定，不用问用户。项目确实写了（包括「不用路由」），照它的。

## 1. 拆任务

- 派新活之前，先确认上一件已经收尾：worktree 和分支清掉了，或者写明为什么留着。没收尾不派新活。
- **刚接手、或者不确定还开着谁时，跑一次 `corral ls` 核对**：cwd 指的目录已经不存在的，是上一任主控留下的残骸——工作目录没了，那个 agent 干不了活。名字后面的数字后缀不是判据（`--unique` 第一次开就补 `-1`），判据只有 cwd 在不在。列给用户问关不关，**不要自己关**：你分不清哪个是用户自己在用的。

  ```sh
  corral ls | python3 -c 'import json,os,sys;[print(a["name"],a["cwd"]) for a in json.load(sys.stdin)["agents"] if not os.path.isdir(a["cwd"])]'
  ```
- 架构级的决定（数据模型、模块边界、里程碑怎么划）不要自己拍板：已经有方案或开发计划的，照它拆；没有的，先问用户要不要先定架构，等他给了结论再拆。
- 一件事、一个 agent、一个分支、一个 git worktree。一个 agent 一次只做一件事。
- 地基（数据模型、公共约定）先串行做完，再按需并行，不要一开始就开很多个。
- 并行之前：
  - 把接口约定写进任务文件（字段名照写），两边照同一份约定做；
  - 查文件范围：两个任务要改同一批文件，就不并行，改成先后；
  - 指定谁负责集成（例如后端合并后，由前端 agent 接真实接口验收）。
  - **有集成关系的两半不分别合并**：两个 worktree 都留着，集成验过再一起合并、一起清、一起关。先合并的那半 worktree 一清，它的 agent 就废了，集成时发现要返工只能重开。
- 拿不准的设计问题，可以分别问一个 Claude Code 和一个 Codex，把分歧列给用户，不要自己挑一个就开工。

## 2. 写任务文件

开出来的 agent 看不到你和用户的对话，所以每次委派都先写任务文件。**任务书只写做成什么、范围、怎么算做完，不写怎么证明**：在验证预算内怎么验，由对方自己判断。任务书写得越重，对方做得越重。

模板。没有内容的节整节删掉，不要为了填满而写：

```markdown
# 任务：<一句话>

<日期>，<你的名字> 交给 <对方名字>（<哪家 agent>，<档：模型 / 强度>）。
路由：<见第 3 节的记录格式>
你是被委派的 agent：照本文件做，不要再开别的 agent。

## 先读
- <和这件事直接相关的文件，写到节名，例如「docs/设计.md 第 4 节」。不要整份读交接文件、README>

## 在哪里干活
- worktree：<路径>，分支 <分支>（已从 main 建好）。只动 <目录或文件>。
- <要装依赖才写：命令>
- <有并行任务才写：谁在哪个分支动哪些目录；你不要动 <目录>>

## 要做的
<目标和要求。和别的任务之间的接口约定照写字段名。用户说的「好看」「优雅」这类，译成两三条能看出来的规则>

## 怎么算做完
- <一条条能检查的结果。用户给了验收原话的，照抄，不补不改>
- 验证只做这些：<照第 3 节影响面那一档的预算写具体命令或检查>。觉得不够，在回复里说，不要自己加。

## 不要做
- <范围外的事>
- 不要按项目名或路径批量杀进程（`pkill -f <项目名>` 这类）：主控和别的 agent 的进程命令行里都带着项目名和工作目录，一条命令能把它们全杀掉。停自己起的服务用起的时候记下的 PID，或者固定端口后 `lsof -ti:<端口>`。
- 遇到 <某种情况>，停下来报告，等决定，不要自己换别的办法。
- 不合并到 main，不推送。只在 <分支> 上提交。

## 做完
在本文件末尾追加「## 完成记录」（在你的分支里提交）：做了什么、验证了什么、拿主意的地方、没做的事，各几句话。回复里只写这几样，加上有没有要主控决定的事。命令都在前台跑完，全部做完后，回复最后一行写 DONE。
```

写完自查一遍，删掉这些：

- 超出预算的验证：覆盖矩阵、跑全套、录屏截图、交证据目录、往代码里植入缺陷看测试红不红。只有「碰要害」那档才可能要，见第 3 节。
- 用户没要的东西：用户的顾虑被你扩成了新功能的，先问用户，不要直接写进去。用户给了验收原话的，验收就是那几条，不补验收点；你觉得该加的，列出来问用户。
- 「主控会审查、会重跑」这类话：只会让对方多做证明。
- 以前某件活的教训：这件活有同样的风险才写，不当成每件的默认条款。

## 3. 交给哪家、几档、要不要交叉审查

每件活都要定这几样。交给哪家由你照下面的分工表定，不问路由；几档、要不要交叉审查、影响面先问路由，路由拿不准再自己按下面的规则定。项目 AGENTS.md 写了的，以及下面「很费 token」的配置，先于这些规则。

**问路由**：写一段任务摘要，三五句，中文即可：做什么、改哪些目录、做错了会影响什么，不写私人数据。不写打算怎么验证：摘要里写了测试矩阵、录屏，路由就会照着判重。运行本技能目录下的 route.py（和这份 SKILL.md 在同一个目录）：

```sh
echo "<摘要>" | python3 <本技能目录>/route.py
```

- 输出里每一项的 `verdict` 就是结论，照用：`tier.verdict`（轻 / 常规 / 重）、`cross_review.verdict`（要 / 不要）、`impact.verdict`（看得见 / 改行为 / 碰要害）。
- 某一项是 `null`（拿不准），或者输出 `"ok": false`（没有 key、网络不通等），这一项自己按下面的规则定，不要重试、不要问用户。项目写了「不用路由」时不调用。
- 只有在知道路由看不到的情况时（比如这件活返工过、审查发现过问题），才推翻它的结论，写一句理由。
- 在任务文件开头记一行：`路由：<档> / 交叉审查<要或不要> / 影响面：<档>（路由：<各项结论，null 写拿不准，不可用写原因>；推翻：<理由，没有就不写>）`。

**交给哪家**：

| 家 | 负责 |
|---|---|
| Claude Code | 设计和品味：架构、模块边界、数据库设计方案；界面和交互方案；界面实现（网页、终端）；配色、文案这类要看了才知道好不好的活 |
| Codex | 方式已定的实现：照方案写后端、迁移、接口、业务规则；修 bug、补测试、批量机械改动、跑很久的活；两家都做得了的活；交叉审查；前端做完的浏览器验收 |
| pi、omp | 项目代码之外的杂活：本机清理、一次性脚本、核对数据、跑命令汇报。两家同类，任选，一家手上有活就开另一家。只接轻档；项目代码里的改动再小也不给它 |

- 既要设计又要实现的，拆成两步：Claude 出方案，用户定（架构级的决定照第 1 节由用户拍板），再派人实现。界面活例外，实现也给 Claude。
- 新界面、或者没有现成示意的大改，派人实现之前先给用户看样子：一张文字线框或示意，用户选定了再派。规则明确的小调整（换个颜色、加一个提示）直接做。
- 拿不准哪家做得了，给 Codex：别用 Claude Code 的额度做 Codex 也能做的事。这条按订阅定——现在 Codex 额度宽松、Claude Code 有周限额；订阅变了改这条。
- 这张表只管派出去的活。用户让你自己动手的（比如小的样式调整），直接做，不用派。
- **一件活一个 agent、一个 worktree**：新活不要塞给已经开着的写代码 agent，它的工作目录钉在自己那个 worktree 上，换不了目录，也换不了模型和强度。同一个 agent 只在自己那个 worktree 里接后续：返工、复核。要稳定的是「家」不是实例——同类活固定交给同一家，不要在两家之间来回换。

**几档**：不带参数时，开出来的 agent 用它自己的全局默认，**不继承你的模型和强度**。每次开 agent 都显式带上参数，并在任务文件和汇报里写明用的哪一档。

| 档 | 什么活 | Claude Code | Codex |
|---|---|---|---|
| 轻 | 查资料、机械改动、按清单改文字、跑命令汇报 | `--model sonnet --effort medium` | `-m gpt-5.6-luna -c 'model_reasoning_effort="medium"'` |
| 常规（默认） | 按任务文件写功能、修一般的 bug | `--model 'opus[1m]' --effort high` | `-m gpt-6-astra -c 'model_reasoning_effort="high"'` |
| 重 | 数据模型、并发和事务、跨模块设计、难查的 bug、交叉审查 | `--model 'opus[1m]' --effort xhigh` | `-m gpt-6-astra -c 'model_reasoning_effort="xhigh"'` |

- 拿不准用常规；审查发现质量不够，再升一档重做。
- 下面这些很费 token，可以提议，但要先问用户，同意了才开：Claude Code 用 `fable`（任何强度）、opus 开 `max`；Codex 开 `ultra`（它还会自己再开子 agent）。用户点名就算同意。
- pi、omp 用它们的默认，不分档。
- 模型名会随版本变，过时了改这张表。

**影响面**：定验证预算，写进任务书「怎么算做完」。难度定模型和强度，影响面定验证，两件事分开定。

| 档 | 什么活 | 开发的验证 | 审查 |
|---|---|---|---|
| 看得见 | 只影响显示、文档、文案、配色，或只读研究；做错了一眼看得出，随时能改回 | `git diff --check`，加一条能直接看出结果的检查。不要求先写失败测试 | 主控看 diff，不重跑套件 |
| 改行为 | 写功能、修 bug，不碰下一档 | 一条针对这件活的测试（修 bug 先写测试，确认它因为这个 bug 失败）+ 项目的标准测试跑一次 | 主控看 diff，重跑一次标准测试 |
| 碰要害 | 数据模型和迁移、并发和事务、安全和隐私、核心规则 | 上一档，加上边角用例。覆盖矩阵、植入缺陷自检只在这一档可以要 | 同上，加交叉审查（第 6 节） |

- 照路由的 `impact.verdict`；它是 `null` 时你按上表判，拿不准定「改行为」，不要往重的一头靠。
- 录屏、真实终端录制、在真浏览器里走一遍：哪一档都不是默认。用户要求了，或者验收除此之外确实查不了，才写进任务书；集成验收只走主路径一遍。

**要不要交叉审查**：见第 6 节。

## 4. 派出去

按 corral 技能开 agent，另外注意：

- 名字用 AGENTS.md 规定的前缀，`--cwd` 指向它的 worktree，agent 命令后面带上这一档的参数。第一句话很短，只让它去读文件：

  ```sh
  corral start demo/dev-backend --unique --cwd <worktree> --label effort=high --label model=gpt-6-astra --prompt "先读 AGENTS.md，再读 <任务文件>，照做。命令都在前台跑完，全部做完后，回复最后一行写 DONE。" -- codex --yolo -m gpt-6-astra -c 'model_reasoning_effort="high"'
  ```

- 用 `--label` 记下这一档的强度和模型：`effort=<medium / high / xhigh>`、`model=<模型名>`，和后面 agent 命令里的参数一致。看板靠它显示每个 agent 的档位；pi、omp 不分档，不带。

- 被委派的 agent 一律免确认启动，中途不弹权限框，也不会被自动检查拦下。agent 命令按下表写，后面接上第 3 节的分档参数：

  | agent | agent 命令 |
  |---|---|
  | Claude Code | `claude --dangerously-skip-permissions` |
  | Codex | `codex --yolo` |
  | pi | `pi`（本来就没有权限框） |
  | omp | `omp --approval-mode yolo` |

  免确认也就没有安全网：能约束它的只剩任务文件里「不要做」那几条，所以那一节要写全。免确认跳不过「是否信任这个目录」的框，见下一条。
- 开完运行 `corral wait <名字> --timeout 60`，不要用 sleep 等。60 秒到了状态还是 `starting`，就是卡在「是否信任这个目录」这类对话框上（新项目、新仓库第一次开时常见）。这时请用户在另一个终端窗口运行 `corral attach <名字>`，或者在看板里选中它去点。不要替它点，也不要让用户在你这里用 `!` 运行。卡在启动中时，提醒不会来，不要干等。
- 写代码都是长任务：按 corral 技能「长任务」一节挂提醒，交出去就结束这一轮。
- 告诉用户：开了谁、哪家哪一档、在哪个 worktree、做什么、做完怎么通知。
- 开出来的 agent 默认不关；写代码的 agent 活到它那个 worktree 被清掉为止（第 7 节）。

## 5. 主控审查：核实，不重做

每件都审，按这件活影响面那一档的预算审（第 3 节），不超出。重点是核实对方说的，不是自己再证一遍：

- 读完成记录和回复，看 diff：只动了该动的，「不要做」里的一件都没做，「怎么算做完」逐条达到。
- 测试：看得见的活不重跑套件；改行为、碰要害的重跑一次项目的标准测试，核对数字和对方说的一致。
- 不自己录屏、不做覆盖矩阵、不另写脚本测边角。真怀疑某一处，挑那一条实测。
- 对方说「用户同意了」「用户说过」的，找用户核实。
- 对方列的取舍逐条表态：同意的记下，不同意的交回去改。
- **只有两种情况交回返工**：「怎么算做完」有一条没达到；做了「不要做」里的事。「没达到」指按验收正常使用会碰到的情况；只在罕见输入组合下才出错的，和清单外发现的边角问题一样记「建议改」，写进审查结论、告诉用户，要不要另开一件活由用户定，不交回返工。
- 结论写三五行，追加到任务文件末尾「## 主控审查」。

要返工的写清楚是哪一条，交回原来的 agent：用 `corral send` 交过去，同样带 DONE 约定、挂提醒。复核只看改动的部分，只重跑和改动有关的检查。

## 6. 交叉审查：只给出错代价大的

只给影响面是「碰要害」的活（第 3 节）：路由的交叉审查结论是「要」，或者你判定它碰了数据模型、并发和事务、安全和隐私、核心规则。看得见、改行为的活不做。

- 另开一个 agent 只读审查，用「重」档。审查一律给 Codex：它更会挑细节。被审的就是 Codex 写的时候，另开一个新的 Codex 实例，只给它任务文件和 diff，不用原来那个。审查任务也写成文件（放主仓库工作区，派的时候给绝对路径，并写明它不在审查 worktree 里、只写这一个文件），依次写：
  - 背景：谁在哪个分支做了什么，主控已经审过什么；
  - 先读；
  - 要审查的代码：**它自己的 worktree**（`git worktree add --detach <审查 worktree> <分支>`；同一个分支不能在两个 worktree 里同时 checkout，git 会拒绝，所以只能 detached，顺带防它手滑提交；也不要和 dev 共用一个，它掉个文件就会挡住清理）、`git diff main...<分支>`，**只读，不改、不提交、不切分支**；写明可以跑哪些测试、不能碰什么；验证照「碰要害」那档的预算，不录屏、不做覆盖矩阵；
  - 重点看：主控列 3 到 5 条，都是这件活碰到的要害；
  - 输出：追加到审查文件「## 审查意见」。先写一句结论（可以合并 / 改完再合并），每条意见写级别（必须改 / 建议改 / 可以不改）、位置、问题、改法，最后对取舍逐条表态。**「必须改」只给两种**：任务书「怎么算做完」没达到；碰到的要害上有真实缺陷（会丢数据、并发出错、泄露或越权、核心规则算错）。其余一律「建议改」；
  - 回复：只写结论和条数，最后一行 DONE。
- 主控逐条判断。只有「必须改」挡合并；「建议改」可以不采纳，写明理由。认可的交给开发 agent 改。
- 改完请同一个审查者复核，只看上一轮的「必须改」修好没有、改动有没有引入新问题；复核时才看到的、和这次改动无关的问题记「建议改」。**先把它的 worktree 推到新提交**：`git -C <审查 worktree> checkout <新 sha>`（仍是 detached）——不推的话它 `git diff` 看得到对象，跑测试却还是旧代码。**复核两轮还没到「可以合并」，停下来问用户**，不再往返。
- 主控和审查者有分歧的，列给用户。

## 7. 合并和收尾

- 合并前：测试全过、主控审查过、要交叉审查的已经是「可以合并」。任务说了不合并的，停在审查，汇报给用户。
- 按 AGENTS.md 的方式合并，合并提交里写一句摘要；推不推送按 AGENTS.md，没写就问。
- 合并后：审查结论追加到任务文件末尾；有集成方在等的，现在通知它。
- **合并后立刻清掉这件活的 worktree 和分支（dev 的和审查的都算），不用问用户。** 按顺序核对，并在回复里说明结果：
  1. 住在这个 worktree 里的 agent 现在是 `idle`（`corral status`）。还在 working 就等它这一轮完，别边跑边删；
  2. `git -C <worktree> status --short` 没有未提交的改动；
  3. 分支已合进 main：`git merge-base --is-ancestor <分支> main`；
  4. `git worktree remove` 不加 `--force`，分支用 `git branch -d` 删；
  5. 关掉住在这个 worktree 里、你自己开的那个 agent（`corral stop`），回复里写一句「工作目录已删，一并关闭」。关掉之后，之前挂在它身上的 `--after` 提醒照样会送到你这里（corral 就是这么设计的），查到 `not_found` 忽略就行。

  第 2 到 4 步是安全构造的：有未提交的改动 `worktree remove` 会拒绝，没合并 `branch -d` 会拒绝，git 自己兜底，丢不了东西。所以不需要等用户点头，**不要攒到下一个里程碑再清**。
- **第 5 步的扳机是第 4 步成功返回，不是你觉得活干完了。** worktree 一删，住在里面的进程 `pwd`、`ls`、`git`、读写文件全部失败，留着也接不了新活。下面三种照旧先问用户：放弃任务要 `--force` 强删（绕过了上面的兜底）、人正 attach 在它上面（`corral status` 的 `attached` 不是 0）、不是你开的 agent。
- 关之前确认记录都落盘了：主控审查结论、交叉审查意见、对方列的取舍都要在任务文件里（主仓库，不随 worktree 消失）——关掉就问不到它了。清完把「还开着哪些、各自在哪」报给用户。
- 项目有交接文件的，更新它。

## 8. 什么自己定，什么先问

- 小事主控先定：写进文档，事后告诉用户。
- 先问用户再做：涉及隐私；花钱（订阅额度、付费服务、真实调用）；改用户批准过的设计；删除东西（**合并后清 worktree 和分支除外**，见第 7 节）；推送；关掉 agent（**清掉 worktree 时一并关掉住在里面、自己开的那个除外**，见第 7 节）。
- 问的方式：一次最多五个问题，按重要程度排，每个问题给选项和你的建议。
